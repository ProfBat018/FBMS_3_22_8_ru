## Архитектура микросервисов

Микросервисы - это архитектурный стиль, при котором приложение состоит из множества небольших сервисов, каждый из которых работает в своем процессе и взаимодействует с другими сервисами посредством HTTP API. Каждый сервис выполняет одну конкретную задачу и может быть разработан, развернут и масштабирован независимо от других сервисов.

На счет HTTP API, на самом деле никто вам не запрещает использовать другой протокол уже внутри ваших сервисов, но внешний интерфейс обязательно должен быть HTTPS. Под другими протоколами я имею ввиду например `gRPC` (его рассмотрим позже).

## Преимущества и недостатки микросервисов

Начнем с того что данную архитектуру придумали еще в 90-х. Расспространил его использование компания `Netflix`. `Google` в свою очередь не особо продвигает данную архитектуру.

### Преимущества

- **Масштабируемость** - каждый сервис можно масштабировать независимо от других сервисов
- **Гибкость** - каждый сервис можно разрабатывать на разных языках программирования
- **Устойчивость** - если один сервис упал, то это не повлияет на работу других сервисов
- **Простота развертывания** - каждый сервис можно развернуть на отдельном сервере и в целом тут работа с Docker весьма упрощает жизнь.

### Недостатки

- **Сложность** - разработка и поддержка микросервисов сложнее чем монолитов(НАМНОГО)
- **Сетевая задержка** - при взаимодействии между сервисами возникает сетевая задержка
- **Сложность отладки** - отладка микросервисов сложнее чем монолитов
- **Сложность тестирования** - тестирование микросервисов сложнее чем монолитов

## Load balancing

Load balancing - это распределение нагрузки между несколькими серверами.

Для этого используются Load Balancer'ы. Они могут быть как аппаратными так и программными.

Аппаратные Load Balancer'ы - это физические устройства, которые распределяют нагрузку между серверами. Такие устройства обычно стоят в дата-центрах, например в `Azure` или `AWS`.
В таком случае ваши данные не сидят на одном носителе, а на нескольких. Это увеличивает надежность вашего приложения. Считайте что функция Local Redundancy в `Azure` это и есть Load Balancer в каком-то роде.

Программные Load Balancer'ы - это программы, которые распределяют нагрузку между серверами. Например `Nginx` или `HAProxy`. Я обещал показать вам `Reverse Proxy` на `Nginx`, так вот это и есть Load Balancer. Давайте разберемся как это работает.

Предположим что у нас есть 1 сервер на котором с помощью `Docker` развернуто 3 контейнера с одним и тем же приложением. На сервере у нас стоит `Nginx` и настроен `Reverse Proxy`. Вот как это выглядит:

![](https://i.sstatic.net/QAvlk.jpg)

Теперь когда к нам приходит запрос, `Nginx` смотрит на заголовок `Host` и на основе этого заголовка решает куда отправить запрос.

## Default Gateway

Default Gateway - это маршрутизатор по умолчанию. Он используется для отправки пакетов на другие сети.

В случае работы с ASP.NET сервисами для того чтобы написать свой `Default Gateway` вам нужно использовать `Ocelot`. Это библиотека которая позволяет вам создать свой `API Gateway`. И хочу отметить что `API Gateway` - это по сути обычный `API` который принимает запросы и перенаправляет их на другие сервисы.

## Load Balancer vs Default Gateway

Многие путают `Load Balancer` и `Default Gateway`. Давайте разберемся в чем разница.

В случае с `Nginx` мы используем `Load Balancer` для того чтобы распределить нагрузку между одинаковыми сервисами на разных серверах(или контейнерах). `Default Gateway` же используется для того чтобы перенаправлять запросы на разные сервисы. Из-за этого сперва `Load Balancer` а потом уже `Default Gateway`.

## Docker Swarm vs Kubernetes

### Docker Swarm

`Docker Swarm` - это оркестратор контейнеров, который встроен в Docker Engine. Он позволяет развернуть и управлять несколькими контейнерами на нескольких хостах. На самом деле это достаточно старый способ управления контейнерами. Сейчас уже используют `Kubernetes`.

На данном этапе вы можете запутаться между `Docker Swarm` и `Docker Compose`. `Docker Compose` - это инструмент для определения и запуска многоконтейнерных Docker-приложений. Он позволяет вам определить все ваши контейнеры в одном файле и запустить их одной командой. `Docker Swarm` же позволяет вам управлять несколькими контейнерами на нескольких хостах.

То есть `Compose` работает на одном хосте, где n контейнеры запускается в одно и то же время. `Swarm` же работает на нескольких хостах, где n контейнеры запускаются на разных хостах.
